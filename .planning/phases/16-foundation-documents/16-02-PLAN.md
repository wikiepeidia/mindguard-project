**ADR-002: NeonDB PostgreSQL Migration**
- Context: SQLite ephemeral trên Vercel serverless (filesystem reset mỗi cold start). Data loss không chấp nhận được cho production. Team đã có NeonDB free tier.
- Options: (1) SQLite + /tmp workaround, (2) NeonDB PostgreSQL, (3) Supabase PostgreSQL
- Decision: NeonDB PostgreSQL — same connection string cho local + production, pool_pre_ping=True, sslmode=require
- Consequences: +Zero data loss risk, +No env-specific config. -NeonDB free tier limits (0.5GB), -Network latency vs local SQLite

**ADR-003: Vercel Serverless Deployment**
- Context: Need deployment platform with zero budget. Vercel free tier supports Python via serverless functions. Constraints: ephemeral filesystem, 10s timeout, cold start.
- Options: (1) Vercel serverless, (2) Railway, (3) Render
- Decision: Vercel — free tier generous, GitHub integration, edge network. Flask adapted: no file writes, NeonDB for persistence, session via DB.
- Consequences: +Free + fast CDN. -10s function timeout limits long operations, -No persistent filesystem (uploads need external storage)

**ADR-004: AI Safety Strategy**
- Context: AI chatbot dùng OpenRouter (DeepSeek, Gemini, Llama) cho fraud prevention guidance. Risk: model có thể trả lời chủ đề nhạy cảm, timeout dài, hoặc response không chắc chắn.
- Options: (1) No guardrails, (2) Prompt-only safety, (3) Hard-block + fallback + timeout
- Decision: Multi-layer safety — hard-block list cho chủ đề nhạy cảm (chính trị/tôn giáo/tự hại) trả lời cứng + hotline 113, timeout 8s (dưới Vercel 10s limit), fallback cảnh báo OTP khi AI không chắc chắn.
- Consequences: +User safety, +Vercel timeout compliant. -Some legitimate queries may be blocked, -Hardcoded block list needs maintenance

**ADR-005: DB-backed Rate Limiting**
- Context: Chatbot endpoints call OpenRouter API (free tier, limited). Need rate limiting to prevent budget drain. Vercel serverless = stateless (no shared memory between invocations).
- Options: (1) In-memory counter, (2) Redis-backed, (3) DB-backed via @limiter
- Decision: DB-backed @limiter — uses existing NeonDB connection, no additional service needed. Applied to /chatbot/api, /chatbot/support, /chatbot/send.
- Consequences: +No extra infrastructure. -Slightly higher latency than in-memory, -DB write per request (acceptable at current scale)
